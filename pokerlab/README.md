# pokerlab

선택한 프로그램의 창을 실시간으로 읽어 상대 레인지와 내 승률을 계산합니다. 창에 보이는 테이블(좌석, 스택, 앞에 놓인 칩, 딜러 버튼, 카드)을 인식하고, 거기서 포지션과 액션 이력을 복원해, 공개 핸드 히스토리로 학습한 레인지 모델로 계산합니다. 그 밑에는 자체 텍사스 홀덤 엔진, 승률(에퀴티) 계산기, 봇 자가대전으로 매일 학습하는 파이프라인이 있습니다. 같은 저장소의 `poker/`와는 완전히 독립적입니다. 계산 부분의 의존성은 NumPy와 pandas뿐이고, 창 인식 단계만 Google Gemini API를 호출합니다.

| 모듈 | 역할 |
|---|---|
| `cards.py` | 카드 표기(`As`, `Td`, `A♠`) 파싱, 169개 스타팅 핸드 분류 |
| `evaluator.py` | 5~7장 족보 평가기 (단건용 순수 Python + 대량용 NumPy 벡터화) |
| `equity.py` | 승률 계산: 전수 계산 또는 몬테카를로, 가중치 레인지, 전원 매치업, 다음 카드별 승률 |
| `preflop.py` | 프리플랍 승률 테이블(169핸드 × 상대 1~9명), 레인지 표기(`TT+, AQs+, 15%`) 파서 |
| `inference.py` | 상대의 액션 이력으로 레인지를 추정하는 모델: 학습(숨은 카드는 EM), 추정, 정확도 평가 |
| `phh.py` | 공개 핸드 히스토리(PHH 형식) 읽기 |
| `table.py` | 테이블에 보이는 것(좌석, 스택, 앞에 놓인 칩, 딜러 버튼, 카드)에서 포지션과 액션 이력을 복원 |
| `vision.py` | 창의 한 프레임을 읽어 그 값들을 돌려주는 인식 단계 (Google Gemini) |
| `follow.py` | 창 하나를 따라가는 추적기: 새 핸드 감지, 프레임 이어 붙이기, 기록 |
| `advisor.py` | 한 상황을 숫자·한국어 해석·JSON으로 정리 |
| `web.py`, `static/` | 창을 소스로 받아 실시간으로 읽는 로컬 웹 화면. 카드를 직접 넣는 계산기도 들어 있음 |
| `engine.py` | 노리밋 홀덤 한 판 진행 (블라인드, 최소 레이즈, 올인, 사이드팟, 스플릿) |
| `bots.py` | 봇: `station`, `random`, `maniac`, 에퀴티 기반 `nit`/`tag`/`lag`/`tag_range`/`tag_model`, 학습된 `champion`, 실전 데이터의 습관대로 치는 `human`/`pro` |
| `selfplay.py` | 봇끼리 자동 대전시키고 모든 핸드를 SQLite에 누적 (멀티프로세스, 중단 후 이어하기) |
| `report.py` | 누적 DB에서 봇별 bb/100, 포지션·인원·핸드별 통계 |
| `daily.py` | 하루 한 번 도는 학습 사이클: 대전 → 학습 → 검증 → 기록 |

## 설치와 실행

저장소 루트에서 바로 실행하거나, 설치해서 `pokerlab` 명령으로 씁니다.

```bash
python -m pokerlab --help
```

```bash
pip install -e .
```

### 웹 화면: 창을 골라 실시간으로 읽기

```bash
python -m pokerlab serve
```

읽을 프로그램이 떠 있는 컴퓨터의 브라우저에서 `http://127.0.0.1:8765` 를 엽니다. 첫 화면이 "실시간 인식"입니다. "창 추가"를 누르면 브라우저가 창 목록을 보여 주고(데스크톱 Chrome, Edge, Firefox), 고른 창이 OBS의 소스처럼 소스 하나가 됩니다. 프로그램마다 소스를 따로 두어 각각 따로 인식하고 따로 추적합니다(8개까지).

상대 포지션, 액션, 벳 크기, 올인, 스택 깊이는 고르지 않습니다. 창에 보이는 값만 읽고 나머지는 거기서 계산합니다.

- **소스별 설정**: 이름(프로그램 이름), 다시 읽는 최소 간격(2~10초), 인식 메모. 메모에는 그 프로그램 화면의 특이한 점을 적습니다("스택은 칩 단위, 내 자리는 왼쪽 아래"). 인식 단계에 그대로 전달됩니다.
- **변화가 있을 때만 읽음**: 창의 축소 화면을 0.4초마다 비교해, 화면이 바뀐 뒤 멈췄을 때만 인식을 요청합니다. 바뀌지 않는 화면은 다시 읽지 않습니다.
- **소스 선택**: 소스를 누르면 오른쪽에 그 창에서 읽은 테이블과 승률, 팟 오즈, 상대별 추정 레인지가 나옵니다. 모델을 바꾸면 창을 다시 읽지 않고 다시 계산합니다.
- **기록**: `python -m pokerlab serve --record hands.jsonl`로 띄우면 따라간 핸드가 끝날 때마다 한 줄씩 저장됩니다(소스 이름, 좌석, 버튼, 내 카드, 보드, 액션 기록, 읽은 값).

| 단계 | 하는 일 |
|---|---|
| 인식 (`vision.py`) | 창의 한 프레임에서 좌석별 이름·위치·스택·앞에 놓인 칩·카드 보유 여부, 딜러 버튼, 내 카드, 보드, 팟, 블라인드, 누구 차례인지를 읽음 |
| 추적 (`follow.py`) | 소스마다 지금 치는 핸드를 유지: 새 핸드 감지, 프레임 이어 붙이기, 끝난 핸드 기록 |
| 처리 (`table.py`) | 좌석을 시계 방향으로 정렬하고, 버튼에서 포지션과 테이블 크기를, 칩의 변화에서 각 플레이어의 폴드·콜·레이즈와 금액을 복원 |
| 계산 | 복원한 액션 이력을 봇이 쓰는 것과 같은 경로로 모델에 넣어 상대별 레인지와 내 승률, 팟 오즈를 계산 |

인식 단계가 읽는 것은 화면에 그대로 보이는 값뿐이고, 포지션이나 "누가 레이즈했는가"는 묻지 않습니다. 그런 값은 읽은 숫자에서 규칙으로 계산합니다.

**아무 때나 들어오는 프레임을 어떻게 잇는가.** 창은 내 차례가 아닐 때의 화면도 보냅니다. 인식 단계가 "누구 차례인가"(강조된 자리, 타이머, 내 액션 버튼)를 함께 읽고, 추적기는 그것을 써서 칩의 변화를 액션으로 풉니다. 엔진이 친 핸드를 프레임으로 바꿔 넣고 원래 기록과 대조했습니다(2~9인, 100bb 동일 스택과 4~250bb가 섞인 스택, 올인·모자란 콜·사이드 팟 포함).

| 창이 알려 주는 것 | 엔진 핸드와 대조한 결과 |
|---|---|
| 누구 차례인지 보임, 모든 순간의 프레임 | 5,238건 모두 일치 |
| 누구 차례인지 보임, 프레임의 절반을 놓침 | 5,238건 모두 일치 |
| 차례를 알 수 없음, 모든 순간의 프레임 | 5,238건 모두 일치 (아무도 뒤따라 행동하지 않은 체크는 미정으로 둠) |
| 차례를 알 수 없음, 프레임의 절반을 놓침 | 5,238건 중 5,081건(97.0%) 일치 |

차례를 모르면 체크는 그 뒤에 누군가 행동해야 드러납니다. 그래서 마지막 체크는 추측하지 않고 비워 둡니다. 새 핸드는 내 카드가 바뀌거나 보드가 이어지지 않을 때 시작된 것으로 봅니다. 앞선 프레임과 이어지지 않는 프레임이 오면(잘못 읽은 숫자 등) 멈추지 않고 그 프레임부터 다시 읽으며, 그렇게 했다고 표시합니다.

핸드를 처음부터 따라가는 것이 승률 추정에 얼마나 보탬이 되는지도 쟀습니다. `human` 봇 6인 테이블(스택 25~200bb)의 결정 시점 3,541개에서, 상대가 실제로 든 핸드 기준 승률과의 평균 오차입니다.

| | 랜덤 핸드 가정 | 지금 스트리트만 읽음 (핸드 중간에 창을 잡은 경우) | 핸드를 처음부터 따라감 |
|---|---|---|---|
| 전체 (3,541) | 8.50%p | 7.86%p | 7.61%p |
| 그 핸드의 두 번째 이후 결정 (502) | 22.1%p | 20.3%p | 18.6%p |

**키.** 인식은 Google Gemini API를 씁니다. 키는 환경 변수로 줍니다. 프레임은 인식을 위해 Google로 전송되며(저장 안 함 옵션으로 호출), 창에 보이는 다른 플레이어의 닉네임이 함께 나갑니다. `POKERLAB_VISION_MODEL`로 모델을 바꿀 수 있습니다(기본 `gemini-4-hydrogen`).

```bash
export GEMINI_API_KEY=...
```

**화면 인식 없이 상태를 직접 보내기.** 직접 만든 게임처럼 자기 상태를 아는 프로그램은 프레임 대신 값을 바로 보낼 수 있습니다. `POST /api/capture`에 `image` 대신 `snapshot`을 넣으면 같은 추적과 계산을 거쳐 응답으로 분석을 돌려줍니다. 지금은 응답으로만 돌려주고, 이렇게 보낸 소스는 웹 화면의 소스 목록에 나타나지 않습니다.

```json
{"source": "my-game", "snapshot":
 {"hero": "AsKd", "board": "Qs7h2d", "pot": 23, "big_blind": 2, "hero_to_act": true,
  "seats": [{"name": "A", "x": 0.5, "y": 0.9, "stack": 194, "bet": 0, "in_hand": true, "hero": true},
            {"name": "B", "x": 0.5, "y": 0.1, "stack": 184, "bet": 10, "in_hand": true, "button": true}]}}
```

**아직 확인하지 못한 것.** 위 수치는 "읽은 값이 맞다면"의 결과입니다. 실제로 돌려 본 것은 인식 이후의 단계입니다. 브라우저 시험은 창 선택을 대신하는 가짜 영상과, 인식을 대신하는 저장된 값 재생(`POKERLAB_VISION_REPLAY=값.json`)으로 했습니다. 실제 창 선택 대화상자와 실제 Gemini 인식은 Gemini API 키가 없어 한 번도 돌려 보지 못했습니다. 인식 한 번에 몇 초가 걸리고 호출마다 비용이 들며, 프로그램 화면에 따라 읽기 정확도가 다를 것입니다.

**직접 계산.** 두 번째 탭은 창 없이 쓰는 계산기입니다. 카드를 클릭해 내 핸드와 보드를 채우면 승률, 승/무/패 비율, 최종 족보 확률, 다음 카드별 승률, 상대 수별 승률이 계산됩니다. 상대를 추가해 액션(예: 오픈 레이즈 → 플랍 벳)을 넣으면 추정 레인지가 13×13 표로 표시되고 승률이 그 레인지 기준으로 바뀝니다.

### 명령줄

```bash
python -m pokerlab equity AsKs --board "Qs Js 2d" --players 2 --position bb --villain "btn: open/bet" --pot 100 --to-call 50
```

```
[플랍] 내 핸드 As Ks (AKs) | 보드 Qs Js 2d | 2명 (상대 1명, 레인지 지정)
승률(에퀴티) 70.79%  = 승 69.72% + 무 2.14% 분배 / 패 28.13%   (전수 계산, 오차 없음)
판정: 강함  (인원 기준 평균 승률 50.0%의 1.42배)
상대1 레인지 (btn: open/bet): 전체 핸드의 약 45% 폭 | 비중 상위 ATo 2%, AQo 2%, QTo 2%, Q9o 2%, AJo 2%, KTo 2%
현재 족보: 하이카드  | 지금 당장 쇼다운이면 랜덤 핸드 1개 상대로 앞섬 59.2% / 동률 0.8% / 뒤짐 40.0%
리버까지 갔을 때 내 최종 족보: 플러시 31.1%, 원페어 28.8%, 하이카드 18.0%, 스트레이트 9.9%, ...
다음 카드별 승률: 스트레이트 플러시 1장 → 100%, 플러시 8장 → 98%, 스트레이트 3장 → 96%, 원페어 14장 → 70%, 하이카드 21장 → 56%
  승률이 10%p 이상 오르는 카드 18장, 10%p 이상 떨어지는 카드 29장 (전체 47장)
팟 오즈: 팟 100에 50 콜 -> 필요 승률 33.3%, 내 승률 70.8% -> 콜 기대값 +56.2 (수익 콜)
```

| 옵션 | 뜻 |
|---|---|
| `--players N` | 지금 판에 남은 인원, 나 포함 (2~10) |
| `--table N` | 테이블에 앉은 인원. 생략하면 6인(남은 인원이 6명을 넘으면 9인)으로 가정 |
| `--range R` | 상대 한 명의 레인지를 직접 지정. `TT+,AQs+`, `15%`, 카드 지정 `QhQd`. 여러 번 가능 |
| `--villain LINE` | 상대 한 명의 액션. 스트리트는 `/`로 구분하며 레인지를 모델이 추정. 좌석과 스택을 알면 `btn 40bb: open/bet`처럼 앞에 붙이고, 벳 크기를 알면 `open3x/bet66/betallin`처럼 단어 뒤에 붙임. 여러 번 가능 |
| `--stack BB` | 핸드를 시작할 때의 유효 스택(빅 블라인드). 스택을 따로 적지 않은 `--villain` 줄에 적용 |
| `--position SEAT` | 내 좌석 (`ep mp co btn sb bb`). 상대 좌석과 함께 주면 플랍 이후 누가 나중에 행동하는지까지 반영 |
| `--model NAME` | 액션을 해석할 모델: `online`(기본), `pro`, `selfplay` 또는 모델 파일. `--profile`로 그 안의 유형 선택 |
| `--pot`, `--to-call`, `--bet` | 팟 오즈, 콜 기대값, 베팅 손익분기 계산 |
| `--precision 0.05` | 95% 신뢰구간이 ±0.05%p가 될 때까지 시뮬레이션 |
| `--json` | 숫자를 JSON으로 출력 |

액션 단어는 프리플랍 `limp open call 3bet call3bet 4bet check`, 플랍 이후 `check bet call raise callraise reraise`입니다. 단어 뒤의 숫자는 팟 대비 크기(%)입니다. `bet66`은 팟의 66% 벳, `raise100`은 콜한 뒤의 팟만큼 올린 레이즈, `call50`은 팟의 절반 크기 벳에 콜한 것입니다. 프리플랍 오픈은 `open3x`, `call3x`(3bb 오픈에 콜)처럼 빅 블라인드 배수로도 씁니다. 숫자 대신 `allin`을 붙이면 올인입니다(`betallin`, `raiseallin`, `callallin`은 올인에 콜, `shove`는 줄임말). 크기를 생략하면 모든 크기의 평균으로 해석합니다.

스택은 핸드를 시작할 때 상대의 칩과 그 상대에 맞선 가장 큰 스택 중 작은 쪽입니다. 스택을 주면 각 액션 시점에 남은 칩이 팟의 몇 배인지를 줄을 따라 계산합니다. 이때 크기를 적지 않은 벳은 흔한 크기(팟의 66%, 오픈 3bb)로, 모든 벳은 한 명이 콜한 것으로 가정합니다. 스택을 생략하면 모든 깊이의 평균으로 해석합니다. 좌석은 `ep`(얼리), `mp`(미들), `co`(컷오프), `btn`(버튼), `sb`, `bb`이고 `utg`, `hj`도 받습니다. 액션 한 줄에는 그때 누가 폴드해 있었는지가 없으므로, 프리플랍은 그 좌석 앞이 모두 폴드한 상황으로 가정합니다.

모든 플레이어의 승률을 한 번에 보려면 `matchup`을 씁니다. 핸드가 전부 정해져 있으면 남은 보드를 전수 계산합니다.


### Python

```python
from pokerlab.equity import equity, matchup, next_card
from pokerlab.inference import range_from_line
from pokerlab.preflop import parse_range

equity("AsKs", "Qs Js 2d", n_opponents=3)                        # .equity .win .tie .ci95 .hand_dist
equity("AsKs", n_opponents=5, precision=0.001)                   # ±0.1%p가 될 때까지
equity("AhKd", ranges=[parse_range("QQ+")])                      # 상대 레인지 지정
equity("AsKs", "Qs Js 2d", ranges=[range_from_line("open/bet", "AsKs", "Qs Js 2d")])
matchup(["AsKs", parse_range("TT+"), None], "Qs Js 2d")          # 핸드, 레인지, 랜덤 핸드
next_card("AsKs", "Qs Js 2d")                                    # {카드: 그 카드가 나온 뒤 승률}
```

## 레인지 추정 모델의 효과

모델은 "어떤 상황에서 어떤 강도의 핸드로 어떤 액션을 했는가"를 센 표입니다. 상대의 액션을 관찰할 때마다 베이즈 규칙으로 1,326개 콤보의 가중치를 갱신합니다.

- **액션**: 폴드, 체크·콜, 벳·레이즈를 크기에 따라 셋으로 나눈 것(작게, 보통, 크게), 그리고 올인. 크기는 콜 금액을 넘겨 넣은 칩을 콜한 뒤의 팟으로 나눈 값이고, 45% 미만이 작게, 90% 이상이 크게입니다. 상대가 받을 수 있는 칩을 전부 넣은 벳은 크기와 상관없이 올인입니다(내 스택이 더 커서 상대만 올인이 되는 벳도 포함).
- **상황**: 스트리트, 그 스트리트에서 이미 나온 레이즈 수, 콜 가격, 스택 깊이, 남은 인원, 테이블 크기(1:1 / 3~6인 / 7인 이상), 포지션.
- **콜 가격**: 콜할 금액을 팟으로 나눈 값으로, 없음 / 싸다 / 보통 / 비싸다 네 단계입니다. 경계는 팟의 45%와 90% 크기 벳이 만드는 가격(0.31, 0.47)입니다.
- **스택 깊이**: 콜한 뒤에도 더 걸 수 있는 칩(내 칩과 상대 중 가장 큰 스택 가운데 작은 쪽)을 콜한 뒤의 팟으로 나눈 값으로, 다섯 단계입니다. 남은 칩 없음(올인을 받았거나 콜하면 올인) / 팟 1배 미만 / 1~4배 / 4~20배 / 20배 이상. 100bb로 시작하면 프리플랍 첫 액션이 20배 이상, 플랍이 4~20배, 벳이 이어진 리버가 1~4배쯤입니다.
- **포지션**: 프리플랍은 좌석(얼리, 미들, 컷오프, 버튼, 스몰 블라인드, 빅 블라인드), 플랍 이후는 남은 플레이어 중 행동 순서(처음, 중간, 마지막).
- **핸드 강도**: 그 보드에서 가능한 모든 핸드 중 상위 몇 %인지를 10구간으로 나눈 값.
- **드문 상황**: 상황은 굵은 것에서 세밀한 것으로 포개져 있고, 각 단계는 자기 데이터에 윗단계 확률 20회분을 더해 추정합니다. 몇 번 못 본 좌석은 그 테이블의 평균에 기대게 됩니다.
- **벳 종류의 추정**: 벳이 세 크기와 올인 중 무엇인지는 폴드·콜·벳 확률과 따로 추정합니다. 모든 강도의 핸드가 함께 쓰는 분포에서 출발하고, 상황을 좁힐 때는 먼저 모든 강도를 똑같이 옮긴 뒤(남은 칩이 적으면 어떤 핸드든 벳의 대부분이 올인입니다) 강도별 데이터를 반영합니다. 그래서 데이터가 보여 주는 만큼만 크기가 핸드에 대한 정보가 됩니다.

## 공개 핸드 히스토리로 학습한 모델

사람의 플레이를 읽으려면 사람의 데이터로 배워야 합니다. [PHH 데이터셋](https://github.com/uoftcprg/phh-dataset)(MIT 라이선스)의 두 묶음으로 학습한 모델을 함께 넣었습니다. 분석 도구(`equity`, 웹 화면)는 `online`을 기본으로 쓰고, 봇과 매일 학습은 `selfplay`를 씁니다.

| 모델 | 데이터 | 홀카드 |
|---|---|---|
| `online` | 2009년 7월 6개 사이트의 실전 캐시게임 200,609핸드 (HandHQ, 25NL~1000NL, 2~10인). 스택이 기록된 것은 161,935핸드 | 쇼다운에서 보여준 것만: 플레이어-핸드의 5.2% |
| `pro` | Pluribus와 프로 5명의 6인 게임 10,000핸드 (Brown & Sandholm 2019) | 전부 공개 |
| `selfplay` | 이 패키지의 봇 자가대전, 매일 학습으로 갱신 | 전부 공개 |

`online`에는 스테이크 구간 프로필(`nl25-50`, `nl100-200`, `nl400-600`, `nl1000`)이, `pro`에는 `pluribus`와 `pro` 프로필이 들어 있습니다. HandHQ 파일의 203,204핸드 가운데 블라인드가 음수로 적힌 2,595핸드는 팟 크기를 알 수 없어 뺐습니다. 스택이 기록되지 않은 38,674핸드(일부 사이트)는 폴드·콜·벳 학습에는 쓰고, 스택 깊이와 올인 학습에서는 뺍니다. Pluribus 데이터는 모든 핸드가 100bb로 시작합니다.

### 숨은 카드를 다루는 방법

실전 기록에서는 폴드한 핸드를 볼 수 없습니다. 보여준 핸드만 세면 끝까지 간 핸드만 남아 모델이 틀어집니다. 그래서 EM을 씁니다. 현재 모델로 각 플레이어의 숨은 핸드가 무엇이었을지를 그 판의 모든 액션을 근거로 추정하고, 그 확률만큼 나눠 세고, 다시 추정하기를 반복합니다. 카드가 공개된 플레이어는 그대로 한 번씩 셉니다.

학습은 2단계입니다. 먼저 테이블 크기와 포지션을 뺀 굵은 상황으로 수렴시키고, 그 답에서 출발해 세밀한 상황을 학습합니다. 두 단계 모두 숨은 핸드를 추정할 때는 폴드·콜·벳만 보고, 벳 크기와 콜 가격, 스택 깊이와 올인은 그 추정에 따라 세기만 합니다(이유는 아래 '벳 크기와 콜 가격의 효과'). 세밀한 상황을 백지에서 바로 학습하면 실전 데이터에서 강한 핸드와 약한 핸드의 구분이 흐린 모델이 나왔습니다. 가장 약한 10% 핸드의 오픈 레이즈 빈도가 6%였고, 2단계 학습에서는 1%입니다.

정답을 아는 자가대전 데이터로 절차를 확인했습니다. 6만 핸드에서 실전 기록과 같은 비율(플레이어-핸드의 5.2%)만 카드를 남기고 학습한 뒤, 새 핸드 2,500개로 평가했습니다.

| 학습 방법 | 전체 정보 모델과의 확률 차이 | 액션당 로그우도 | 승률 평균 오차 |
|---|---|---|---|
| 전체 정보로 학습 (기준) | 0 | −0.399 | 11.79%p |
| EM 2단계 (카드 5.2%만 공개) | 3.5% | −0.417 | 11.78%p |
| EM 2단계, 벳 크기와 콜 가격도 추정에 사용 | 3.4% | −0.416 | 11.74%p |

로그우도는 벳 크기까지 맞히는 기준입니다. 봇은 핸드 강도에 따라 기계적으로 행동해서, 벳 크기를 넣기 전의 측정에서는 백지에서 한 번에 학습해도 결과가 같았습니다(확률 차이 3.0%). 2단계가 차이를 만든 것은 실전 데이터입니다.

### 실전 데이터에서의 결과

| 모델 | 액션당 로그우도 | 공개 핸드 적중 |
|---|---|---|
| `selfplay` | −1.600 | 0.00배 |
| `pro` | −0.832 | 1.32배 |

`selfplay`의 0.00배는 봇이 절대 하지 않는 액션(약한 핸드의 레이즈 등)을 사람이 하기 때문입니다. 그런 핸드에 거의 0의 확률을 주면 기하평균이 0으로 떨어집니다.

승률 추정의 정확도는 모든 홀카드를 아는 Pluribus 데이터로 쟀습니다. 1만 핸드에서 결정 시점을 하나씩 뽑았고, `pro`는 5겹 교차검증(학습에 쓰지 않은 핸드로 평가)입니다.

|---|---|---|---|

### 벳 크기와 콜 가격의 효과

모델에 담긴 습관의 예입니다(`online`). 둘만 남은 리버에서 체크가 돌아왔을 때 벳한 핸드 가운데 작은 벳과 큰 벳의 비율이며, 가장 약한 10% 핸드에서 가장 강한 10% 핸드 순서입니다.

| 리버 벳의 크기 | 최약 | | | | | | | | | 최강 |
|---|---|---|---|---|---|---|---|---|---|---|
| 작게 (팟의 45% 미만) | 16% | 20% | 21% | 23% | 28% | 32% | 35% | 34% | 27% | 19% |
| 크게 (90% 이상) | 26% | 25% | 21% | 21% | 19% | 18% | 16% | 14% | 15% | 20% |
| 올인 | 5% | 5% | 6% | 8% | 10% | 7% | 8% | 9% | 12% | 15% |

작은 벳은 중간 강도 핸드에서, 큰 벳은 아주 약하거나 아주 강한 핸드에서 상대적으로 많습니다. 플랍에서는 강도에 따른 차이가 작습니다(작게 9~13%, 크게 13~22%).

콜 가격은 폴드 빈도를 바꿉니다. 둘만 남은 리버에서 벳을 받았을 때 폴드하는 빈도입니다.

| 받은 벳 | 최약 | | | | | | | | | 최강 |
|---|---|---|---|---|---|---|---|---|---|---|
| 싸다 (팟의 45% 미만) | 93% | 92% | 84% | 85% | 67% | 50% | 39% | 24% | 10% | 1% |
| 보통 | 95% | 96% | 93% | 93% | 80% | 69% | 55% | 39% | 16% | 2% |
| 비싸다 (90% 이상) | 99% | 99% | 97% | 96% | 87% | 77% | 71% | 52% | 24% | 2% |

분석 도구에서는 같은 액션이라도 크기에 따라 결과가 달라집니다. 내가 버튼에서 A♠K♣로 매 스트리트 벳했고 빅 블라인드가 모두 콜한 경우입니다(보드 K♠9♦4♣7♥2♠).

| 빅 블라인드의 액션 | 추정 레인지 폭 | 내 승률 |
|---|---|---|
| `bb: call/call/call/call` (크기 모름) | 18% | 82.1% |
| `bb: call3x/call33/call33/call33` (매번 팟의 1/3 벳에 콜) | 22% | 86.9% |
| `bb: call3x/call100/call100/call100` (매번 팟 크기 벳에 콜) | 15% | 72.5% |

크기를 넣으면서 학습 절차를 하나 바꿨습니다. 처음에는 숨은 카드를 추정할 때 벳 크기와 콜 가격까지 근거로 썼는데, 그렇게 학습한 모델은 보류 핸드의 공개 핸드 적중이 크기를 쓰지 않을 때보다 낮았습니다(2.08배 대 2.20배). 큰 벳은 상대가 폴드해서 카드가 공개되지 않고 끝나는 일이 많고, 그런 핸드를 EM이 자기 추정으로 채우면서 "큰 벳은 약한 핸드"라는 쪽으로 쏠렸습니다. 플랍에서 약한 쪽 30% 핸드가 벳했을 때 큰 벳의 비율이 그 모델에서는 46%였는데, 보류 핸드에서 실제로 공개된 그런 벳 122건에서는 23%였습니다. 지금은 숨은 카드를 추정할 때 크기와 가격을 보지 않고, 추정된 핸드에 따라 크기별로 세기만 합니다. 이렇게 학습한 모델에서는 같은 비율이 21%입니다. 공개된 핸드는 쇼다운까지 간 핸드라 전체를 대표하지는 않지만, 보류 핸드의 적중도 이 절차가 가장 높았습니다.

정답을 아는 자가대전 데이터에서는 결과가 반대였습니다. 봇은 약한 핸드로 큰 벳을 하지 않는데(플랍에서 약한 쪽 40% 핸드의 벳 중 큰 벳 0%), 크기까지 추정에 쓴 학습은 이를 그대로 복원했고(0~1%) 지금 절차는 흐리게 복원했습니다(9~12%). 전체 지표는 위 표처럼 비슷합니다. 봇은 핸드 강도만으로 행동하지만 사람은 플레이어마다 크기 습관이 다르고, 그 습관까지 숨은 핸드 탓으로 돌리면 틀리는 것으로 보입니다. 지금 절차는 크기의 정보를 덜 쓰는 쪽으로 틀리는 보수적인 선택이며, `fit-history --use-sizes`로 바꿀 수 있습니다.

- 승률 추정 오차는 Pluribus 데이터에서 아주 조금 줄었습니다. `online` −0.02 ± 0.02%p, 리버만 보면 −0.43 ± 0.27%p입니다. 이 데이터는 모든 핸드가 100bb로 시작하고 올인이 벳의 1~2%(리버 11%)뿐이라 차이가 날 자리가 적습니다.
- 봇의 습관으로 프로를 읽는 경우는 또 나빠졌습니다(마지막 행). 봇은 팟에 묶였을 때 강한 핸드로만 올인하는데, 사람은 그렇지 않습니다.
- 스택 깊이와 올인을 숨은 카드 추정에까지 쓰는 학습은 따로 비교하지 않았습니다. 벳 크기에서 확인한 것과 같은 이유로 쓰지 않는 쪽을 택했습니다.

### 사람처럼 치는 봇

`human`과 `pro` 봇은 각 상황에서 자기 핸드 강도 구간의 폴드, 콜, 크기별 벳, 올인 빈도를 모델에서 찾아 그 비율대로 행동합니다. 상황에는 그때 남은 스택도 들어갑니다. 벳 크기는 고른 구간 안에서 무작위로 정합니다(작게 팟의 25~44%, 보통 50~80%, 크게 90~130%). 모델이 데이터를 제대로 담았다면 이 봇의 통계가 원본 데이터와 같아야 합니다.

| | 봇끼리 대전 VPIP / PFR | 원본 데이터 VPIP / PFR |
|---|---|---|
| `human`, 1:1 | 52.6% / 36.6% | 53.0% / 35.5% (1:1 테이블) |
| `human`, 6인 | 25.8% / 15.0% | 28.0% / 16.2% (3~6인 테이블) |
| `human`, 9인 | 21.7% / 9.0% | 21.4% / 9.3% (7~10인 테이블) |
| `pro`, 6인 | 26.7% / 17.9% | 26.3% / 17.6% |

원본의 3~6인 묶음에는 3~5인 테이블도 들어 있어, 6인만 앉힌 봇 테이블보다 조금 느슨한 것이 맞습니다. 봇은 매 핸드 100bb로 시작하고 원본에는 여러 스택이 섞여 있다는 차이도 있습니다.

벳과 레이즈의 종류(작게 / 보통 / 크게 / 올인)도 원본과 비슷합니다. 원본에는 숏스택이 있어 올인이 조금 더 많습니다.

| | 프리플랍, 봇 | 프리플랍, 원본 | 플랍 이후, 봇 | 플랍 이후, 원본 |
|---|---|---|---|---|
| `human`, 1:1 | 1 / 18 / 80 / 1% | 1 / 20 / 78 / 2% | 11 / 63 / 23 / 3% | 12 / 61 / 23 / 4% |
| `human`, 6인 | 7 / 45 / 47 / 1% | 10 / 44 / 42 / 4% | 20 / 61 / 14 / 5% | 22 / 59 / 13 / 7% |
| `human`, 9인 | 15 / 42 / 42 / 1% | 16 / 42 / 38 / 5% | 32 / 47 / 16 / 5% | 34 / 44 / 14 / 8% |
| `pro`, 6인 | 22 / 55 / 22 / 1% | 22 / 56 / 22 / 1% | 25 / 56 / 15 / 4% | 27 / 55 / 15 / 3% |

스택 깊이별로 나누면 올인 빈도가 맞는지 더 직접 볼 수 있습니다. 6인 테이블에서 벳·레이즈 가운데 올인의 비율입니다.

| 남은 칩 | 프리플랍: 100bb 봇 / 20bb 봇 / 원본 | 플랍 이후: 100bb 봇 / 20bb 봇 / 원본 |
|---|---|---|
| 팟 1배 미만 | 98% / 97% / 93% | 81% / 84% / 75% |
| 팟의 1~4배 | 55% / 64% / 61% | 9% / 7% / 7% |
| 팟의 4~20배 | 4% / 3% / 4% | 0% / 0% / 0% |

올인을 받았을 때 콜하는 비율은 100bb 봇 55%, 원본 55%입니다.

이 봇 3명이 앉은 6인 테이블(6만 핸드)에서 에퀴티 봇의 성적은 `tag`(레인지를 읽지 않음) −56 ± 11, `tag_model` +29 ± 8, `online` 모델로 읽는 봇 +23 ± 8 bb/100이었습니다. 레인지를 읽으면 손실이 수익으로 바뀌지만, 어느 모델로 읽는지는 이 대전에서 차이가 없었습니다. 1:1에서는 `human`이 `tag`를 조금 앞섰고(`tag` −29 ± 22), `online` 모델로 읽는 봇은 +39 ± 14였습니다. 스택 깊이와 올인을 넣기 전(−54, +32, +34, −5, +55)보다 `human` 봇이 조금 더 잘 버티는 쪽이지만, 차이는 각 신뢰구간 안팎입니다.

### 모델을 쓰는 봇의 성적

`tag_model`은 `tag`와 베팅 규칙이 같고, 승률을 랜덤 핸드 가정 대신 추정 레인지 기준으로 계산한다는 점만 다릅니다. 각 3만 핸드 결과입니다.

| 대전 | `tag_model`의 bb/100 (95% 신뢰구간) |
|---|---|
| 1:1, 상대 `tag` (랜덤 핸드 가정) | +316 ± 24 |
| 1:1, 상대 `tag_range` (레이즈한 상대를 상위 20%로 가정) | +95 ± 15 |
| 6인 (`tag`, `tag_range`, `nit`, `lag` 2명과 함께) | +131 ± 17 |

6인 리그의 나머지 봇은 `tag_range` +78, `nit` +8, `tag` −7, `lag` −105 bb/100이었습니다. 스택 깊이와 올인을 넣기 전(+334, +95, +140), 벳 크기를 넣기 전(+341, +99, +127)과 오차 범위 안에서 같습니다.

## 한계

- `online` 모델은 2009년 온라인 캐시게임, `pro` 모델은 한 번의 실험에 참가한 프로들의 플레이입니다. 지금의 게임이나 특정 상대의 습관과는 다를 수 있습니다.
- 챔피언과 `selfplay` 모델은 이 봇 풀의 플레이에서 배운 것이라 사람 상대 수익률로 읽으면 안 됩니다.
- 레인지 모델의 상황 구분은 거칩니다(벳 크기와 콜 가격 각 3단계, 스택 깊이 5단계, 레이즈 수 0/1/2+, 남은 인원 2/3/4/5+, 테이블 크기 3단계).
- 스택 깊이는 실전 데이터에서 숏스택과 올인 상황을 읽는 데만 도움이 됐습니다. 100bb로만 치는 자가대전과 Pluribus 데이터에서는 차이가 없거나 아주 작았습니다. 봇은 매 핸드 100bb로 시작하므로 `selfplay` 모델은 프리플랍 숏스택 상황을 본 적이 없습니다.
- 액션을 직접 입력할 때 스택 깊이는 가정 위에서 계산됩니다(크기를 적지 않은 벳은 팟의 66%, 모든 벳은 한 명이 콜). 실제 팟과 많이 다르면 스택을 생략하는 편이 낫습니다.
- 벳 크기와 스택 깊이가 승률 추정 오차를 크게 줄이지는 못했습니다. 실전 데이터에서 상대 핸드를 맞히는 정도가 조금씩 올랐고, Pluribus 데이터의 승률 오차는 10.23%p에서 10.20%p가 됐습니다. 봇의 모델을 사람에게 적용하면 오히려 나빠집니다.
- 창 인식은 인식 단계의 정확도를 아직 실제 화면으로 재지 못했습니다. 읽은 값이 틀리면 그 뒤의 계산도 틀리므로, 표에 보이는 값을 확인하고 쓰는 것이 좋습니다. 앤티, 스트래들, 보드를 두 번 까는 테이블은 다루지 않습니다.
- 액션을 직접 입력할 때는 그때 누가 폴드해 있었는지를 모르므로 가정이 들어갑니다(프리플랍은 앞이 모두 폴드, 플랍 이후는 지금 남은 인원 그대로). 림프가 여럿 있던 판 같은 경우에는 맞지 않습니다.
- 봇은 단순한 규칙 기반이며 균형 전략(GTO)이 아닙니다.
- 매 핸드 스택을 100bb로 초기화하고 좌석을 섞습니다. 레이크·앤티·토너먼트 구조는 없습니다.
- 승률은 "지금 올인해서 끝까지 갔을 때"의 값입니다. 이후 베팅 라운드와 포지션의 영향은 반영하지 않습니다.
- 전수 계산은 핸드가 모두 정해진 경우, 포스트플랍 상대 1명, 턴·리버 상대 2명(레인지 없음)까지입니다. 나머지는 몬테카를로입니다.
