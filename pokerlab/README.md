# pokerlab

선택한 프로그램의 창을 실시간으로 읽어 상대 레인지와 내 승률을 계산합니다. 창에 보이는 테이블(좌석, 스택, 앞에 놓인 칩, 딜러 버튼, 카드)을 인식하고, 거기서 포지션과 액션 이력을 복원해, 공개 핸드 히스토리로 학습한 레인지 모델로 계산합니다. 그 밑에는 자체 텍사스 홀덤 엔진, 승률(에퀴티) 계산기, 봇 자가대전으로 매일 학습하는 파이프라인이 있습니다. 같은 저장소의 `poker/`와는 완전히 독립적입니다. 계산 부분의 의존성은 NumPy와 pandas뿐이고, 창 인식 단계만 외부 API(기본은 Anthropic Claude, 또는 Google Gemini)를 호출합니다.

| 모듈 | 역할 |
|---|---|
| `cards.py` | 카드 표기(`As`, `Td`, `A♠`) 파싱, 169개 스타팅 핸드 분류 |
| `evaluator.py` | 5~7장 족보 평가기 (단건용 순수 Python + 대량용 NumPy 벡터화) |
| `equity.py` | 승률 계산: 전수 계산 또는 몬테카를로, 가중치 레인지, 전원 매치업, 다음 카드별 승률 |
| `preflop.py` | 프리플랍 승률 테이블(169핸드 × 상대 1~9명), 레인지 표기(`TT+, AQs+, 15%`) 파서 |
| `inference.py` | 상대의 액션 이력으로 레인지를 추정하는 모델: 학습(숨은 카드는 EM), 추정, 정확도 평가 |
| `phh.py` | 공개 핸드 히스토리(PHH 형식) 읽기 |
| `table.py` | 테이블에 보이는 것(좌석, 스택, 앞에 놓인 칩, 딜러 버튼, 카드)에서 포지션과 액션 이력을 복원 |
| `vision.py` | 창의 한 프레임을 읽어 그 값들을 돌려주는 인식 단계 (Claude 또는 Gemini) |
| `check.py` | 이 컴퓨터가 창을 읽을 준비가 됐는지 점검: 인식 서비스·모델·키 확인, 값을 아는 테스트 그림 한 장 읽기 |
| `follow.py` | 창 하나를 따라가는 추적기: 새 핸드 감지, 프레임 이어 붙이기, 쇼다운 카드, 기록 |
| `records.py` | 창에서 따라간 핸드의 기록으로 프로그램별 레인지 모델(`live`)을 학습 |
| `advisor.py` | 한 상황을 숫자·한국어 해석·JSON으로 정리 |
| `web.py`, `static/` | 창을 소스로 받아 실시간으로 읽는 로컬 웹 화면. 카드를 직접 넣는 계산기도 들어 있음 |
| `engine.py` | 노리밋 홀덤 한 판 진행 (블라인드, 최소 레이즈, 올인, 사이드팟, 스플릿) |
| `bots.py` | 봇: `station`, `random`, `maniac`, 에퀴티 기반 `nit`/`tag`/`lag`/`tag_range`/`tag_model`, 학습된 `champion`, 실전 데이터의 습관대로 치는 `human`/`pro` |
| `selfplay.py` | 봇끼리 자동 대전시키고 모든 핸드를 SQLite에 누적 (멀티프로세스, 중단 후 이어하기) |
| `formats.py`, `data/formats/` | 대회 형식 데이터(좌석, 시작 스택, 블라인드 상승, 추가 등록, 종료 조건)와 그 형식대로 테이블을 돌리는 생성기 |
| `report.py` | 누적 DB에서 봇별 bb/100, 포지션·인원·핸드별 통계 |
| `daily.py` | 하루 한 번 도는 학습 사이클: 대전 → 학습 → 검증 → 기록 |

## 설치와 실행

저장소 루트에서 바로 실행하거나, 설치해서 `pokerlab` 명령으로 씁니다.

```bash
python -m pokerlab --help
```

```bash
pip install -e .
```

창 읽기를 쓰려면 Claude 패키지를 함께 설치하고 키를 넣은 뒤, 먼저 점검합니다. `check`는 쓸 인식 서비스와 모델, 키가 어느 환경 변수에 있는지(키 값은 표시하지 않음)를 보여 주고, 값을 아는 테스트용 테이블 그림 한 장을 읽어 걸린 시간, 비용, 맞게 읽었는지를 알려 줍니다. 이 컨테이너에서 Opus 5.5로 5.8초, 약 0.03달러에 모두 맞게 읽었습니다. `--no-read`를 붙이면 설정만 보고 아무것도 보내지 않습니다.

macOS, Linux (키는 그 터미널에서만 유효하므로, 계속 쓰려면 `~/.zshrc`나 `~/.bashrc`에 같은 줄을 넣습니다):

```bash
pip install -e ".[claude]"
```

```bash
export ANTHROPIC_API_KEY=...
```

```bash
python -m pokerlab check
```

Windows PowerShell (`setx`로 넣은 키는 새로 연 터미널부터 적용되므로, 지금 터미널에는 `$env:`로도 넣습니다):

```powershell
py -m pip install -e ".[claude]"
```

```powershell
setx ANTHROPIC_API_KEY "..."
```

```powershell
$env:ANTHROPIC_API_KEY = "..."
```

```powershell
py -m pokerlab check
```

Windows에서는 아래의 `python -m pokerlab ...` 명령을 모두 `py -m pokerlab ...`으로 씁니다.

### 웹 화면: 창을 골라 실시간으로 읽기

```bash
python -m pokerlab serve
```

읽을 프로그램이 떠 있는 컴퓨터의 브라우저에서 `http://127.0.0.1:8765` 를 엽니다. 첫 화면이 "실시간 인식"입니다. "창 추가"를 누르면 브라우저가 창 목록을 보여 주고(데스크톱 Chrome, Edge, Firefox), 고른 창이 OBS의 소스처럼 소스 하나가 됩니다. 프로그램마다 소스를 따로 두어 각각 따로 인식하고 따로 추적합니다(8개까지).

상대 포지션, 액션, 벳 크기, 올인, 스택 깊이는 고르지 않습니다. 창에 보이는 값만 읽고 나머지는 거기서 계산합니다.

- **소스별 설정**: 이름(프로그램 이름), 다시 읽는 최소 간격(2~10초), 읽는 방식, 인식 메모. 메모에는 그 프로그램 화면의 특이한 점을 적습니다("내 자리는 위 가운데, 아래 가운데 인물은 딜러, 앞의 숫자는 핸드 누적 금액"). 인식 단계에 그대로 전달됩니다.
- **읽는 방식**: "정확하게"(기본)는 Claude Opus 5.5로 읽습니다. "아껴서"는 Claude Sonnet 5.5로 먼저 읽고, 추적기가 그 화면을 의심하면(핸드와 이어지지 않음, 칩 합계가 다름, 팟이 칩을 낸 만큼이 아님, 내 자리가 다른 곳, 내 카드가 다름) Opus 5.5로 다시 읽어 그 값을 씁니다. 아래 '읽는 방식 비교'처럼 스택이 숫자로 보이는 프로그램에서는 비용이 약 40% 줄고 결과가 같았지만, 스택이 보이지 않는 화면에서는 잘못 읽은 것을 알아채지 못해 권하지 않습니다.
- **비용 표시**: 소스 상태 줄에 읽은 화면 수, 지금까지 쓴 비용(목록 가격으로 계산한 대략의 값), 한 장에 걸린 평균 시간, 다시 읽은 화면 수가 나옵니다.
- **변화가 있을 때만 읽음**: 창을 160×100으로 줄인 화면을 0.4초마다 비교해, 뚜렷하게 바뀐 점이 있으면 화면이 멈춘 뒤(0.35초) 인식을 요청합니다. 타이머 막대처럼 계속 움직이는 화면은 1.5초가 지나면 그대로 읽습니다. 바뀌지 않는 화면은 다시 읽지 않습니다.
  - 처음에는 48×27 화면의 평균 차이로 판단했는데, 실제 경로 시험에서 칩 숫자나 강조 표시만 바뀐 화면 12장 중 5장을 놓쳤고, 계속 움직이는 화면에서는 아예 읽지 않을 수 있었습니다. 지금은 12장을 모두 감지하고, 타이머가 도는 화면도 15초에 6번 읽습니다.
  - 타이머가 계속 도는 프로그램은 화면이 늘 바뀌므로, 다시 읽는 최소 간격마다 계속 인식을 요청합니다. Claude Opus 5.5로 한 번 읽는 데 약 6초가 걸리므로 창 하나가 시간에 약 500장, 약 11달러입니다. 간격을 늘리면 줄어듭니다.
- **보내는 크기**: 프레임은 긴 변 1280px로 줄여 JPEG(품질 0.92)로 보냅니다. 1280px는 아래 정확도를 잰 크기이고, 1600px보다 이미지 토큰이 3분의 1 적습니다. JPEG는 PNG의 약 4분의 1 크기(Flash 게임 화면 600KB → 150KB)입니다. Flash 게임 4장은 PNG와 똑같이 읽었고, HTML5 게임 4장은 PNG를 읽은 뒤 지시문이 바뀌어 바로 비교할 수는 없지만 틀린 값이 늘지 않았습니다(PNG에서 틀린 내 카드 J♣를 맞게 읽음). 이 컨테이너에서는 속도 차이가 없었고, 업로드가 느린 회선에서 차이가 납니다. 토큰과 비용은 그림 크기(픽셀)로 정해지므로 같습니다.
- **인식 품질**: 정답 없이도 읽기 품질을 잽니다. 한 핸드 안에서는 테이블 위 칩 합계(스택 + 팟)가 변하지 않으므로, 합계가 다른 화면은 스택이나 팟을 잘못 읽은 것입니다. 소스 상태 줄에 "칩 합계가 안 맞은 화면 n/m", "다시 읽음 n번", "내 자리를 다른 곳으로 읽은 화면 n/m"이 나오고(마지막이 화면의 10%를 넘으면 메모에 내 자리를 적으라고 안내), `python -m pokerlab quality hands.jsonl`이 프로그램별로 정리합니다. 시뮬레이션에서 합계 불일치 비율은 실제 오독 비율의 약 0.55~0.75배였습니다(오독 2·5·10·20%일 때 1.5·2.7·6.0·12.0%). 앞에 놓인 칩만 잘못 읽은 경우는 합계에 드러나지 않습니다.
- **소스 선택**: 소스를 누르면 오른쪽에 그 창에서 읽은 테이블과 승률, 팟 오즈, 상대별 추정 레인지가 나옵니다. 모델을 바꾸면 창을 다시 읽지 않고 다시 계산합니다.
- **기록**: `python -m pokerlab serve --record hands.jsonl`로 띄우면 따라간 핸드가 끝날 때마다 한 줄씩 저장됩니다(소스 이름, 좌석, 버튼, 내 카드, 보드, 액션 기록, 쇼다운에서 공개된 카드, 읽은 값).
- **기록으로 배우기**: 기록을 켜 두면 새 핸드가 50개 쌓일 때마다(`--learn-every`) 그 기록으로 `live` 모델을 다시 학습합니다. 모델 선택의 기본값 "이 프로그램에서 기록한 핸드로 보정"은 소스 이름이 같은 프로그램의 기록이 있으면 그 프로그램의 플레이로 상대를 읽고, 없으면 실전 온라인 모델과 똑같이 읽습니다(아래 '기록으로 배우는 모델').
- **소스 이름**: 학습과 프로그램별 모델은 소스 이름으로 묶입니다. 이름 칸을 비워 둔 소스는 어떤 프로그램인지 알 수 없으므로 그 핸드를 학습에 쓰지 않고, 상태 줄에 "이름 없음"이라고 표시합니다. 같은 프로그램은 매번 같은 이름으로 추가해 주세요.

| 단계 | 하는 일 |
|---|---|
| 인식 (`vision.py`) | 창의 한 프레임에서 좌석별 이름·위치·스택·앞에 놓인 칩·카드 보유 여부, 딜러 버튼, 내 카드, 보드, 팟, 블라인드, 누구 차례인지를 읽음 |
| 추적 (`follow.py`) | 소스마다 지금 치는 핸드를 유지: 새 핸드 감지, 프레임 이어 붙이기, 끝난 핸드 기록 |
| 처리 (`table.py`) | 좌석을 시계 방향으로 정렬하고, 버튼에서 포지션과 테이블 크기를, 칩의 변화에서 각 플레이어의 폴드·콜·레이즈와 금액을 복원 |
| 계산 | 복원한 액션 이력을 봇이 쓰는 것과 같은 경로로 모델에 넣어 상대별 레인지와 내 승률, 팟 오즈를 계산 |

인식 단계가 읽는 것은 화면에 그대로 보이는 값뿐이고, 포지션이나 "누가 레이즈했는가"는 묻지 않습니다. 그런 값은 읽은 숫자에서 규칙으로 계산합니다.

**아무 때나 들어오는 프레임을 어떻게 잇는가.** 창은 내 차례가 아닐 때의 화면도 보냅니다. 인식 단계가 "누구 차례인가"(강조된 자리, 타이머, 내 액션 버튼)를 함께 읽고, 추적기는 그것을 써서 칩의 변화를 액션으로 풉니다. 엔진이 친 핸드를 프레임으로 바꿔 넣고 원래 기록과 대조했습니다(2~9인, 100bb 동일 스택과 4~250bb가 섞인 스택, 올인·모자란 콜·사이드 팟 포함).

| 창이 알려 주는 것 | 엔진 핸드와 대조한 결과 |
|---|---|
| 누구 차례인지 보임, 모든 순간의 프레임 | 5,238건 모두 일치 |
| 누구 차례인지 보임, 프레임의 절반을 놓침 | 5,238건 모두 일치 |
| 차례를 알 수 없음, 모든 순간의 프레임 | 5,238건 모두 일치 (아무도 뒤따라 행동하지 않은 체크는 미정으로 둠) |
| 차례를 알 수 없음, 프레임의 절반을 놓침 | 5,238건 중 5,081건(97.0%) 일치 |

차례를 모르면 체크는 그 뒤에 누군가 행동해야 드러납니다. 그래서 마지막 체크는 추측하지 않고 비워 둡니다. 새 핸드는 보드가 이어지지 않거나, 내 카드가 바뀌면서 버튼이 움직이거나 팟이 줄었을 때 시작된 것으로 봅니다. 내 카드만 다르게 읽힌 프레임은 같은 핸드로 두고, 그 핸드의 프레임 대부분이 보여 준 카드를 씁니다. 앞선 프레임과 이어지지 않는 프레임이 오면(잘못 읽은 숫자 등) 멈추지 않고 그 프레임부터 다시 읽으며, 그렇게 했다고 표시합니다.

한 프레임만의 오독은 핸드 전체를 보고 바로잡습니다. 앞뒤 프레임과 달리 한 프레임에서만 폴드했거나 다시 들어온 것으로 읽힌 자리는 앞뒤를 따르고, 나중 프레임에서 아직 핸드에 있는 자리는 그 전에도 있었던 것으로 봅니다(폴드한 사람은 돌아오지 않으므로). 버튼은 핸드 중에 움직이지 않으므로 프레임 대부분이 가리킨 자리로 정합니다. 남은 사람이 하나가 되는 폴드는 다음 프레임도 그렇게 보이거나 팟이 넘어간 뒤에야 핸드를 끝냅니다. 블라인드가 들어가는 중에 찍힌 첫 프레임은 빅 블라인드를 낸 것이 보이는 프레임으로 블라인드를 정합니다.

핸드를 처음부터 따라가는 것이 승률 추정에 얼마나 보탬이 되는지도 쟀습니다. `human` 봇 6인 테이블(스택 25~200bb)의 결정 시점 3,541개에서, 상대가 실제로 든 핸드 기준 승률과의 평균 오차입니다.

| | 랜덤 핸드 가정 | 지금 스트리트만 읽음 (핸드 중간에 창을 잡은 경우) | 핸드를 처음부터 따라감 |
|---|---|---|---|
| 전체 (3,541) | 8.50%p | 7.86%p | 7.61%p |
| 그 핸드의 두 번째 이후 결정 (502) | 22.1%p | 20.3%p | 18.6%p |

**프로그램마다 다른 화면.** 연구용·기록용 프로그램은 일반 게임 화면과 다르게 보여 주는 경우가 많아, 아래 경우를 모두 따라갑니다.

| 화면 | 처리 |
|---|---|
| 내 카드만 보이고, 쇼다운에서 상대 카드가 뒤집힘 | 뒤집힌 카드를 기록하고, 마지막 라운드의 남은 체크를 채운 뒤 더는 칩을 읽지 않음 |
| 모든 플레이어의 카드가 처음부터 보임 | 칩을 그대로 읽고, 보이는 카드는 모두 기록. 내 승률은 상대의 실제 카드로 정확히 계산 |
| 폴드한 뒤에도 내 카드가 남아 있음 | 내가 폴드한 것으로 읽고 핸드 끝까지 따라감. 화면에는 남은 플레이어들의 승률 |
| 폴드하면 내 카드가 사라지지만 내 자리는 표시됨 | 같은 핸드의 내 카드로 채워 끝까지 따라감 |
| 내 자리가 없는 관전 화면 (카드 공개 또는 비공개) | 버튼으로 핸드를 구분해 따라가고, 모든 플레이어의 승률을 보여 줌 (보이는 카드는 그대로, 안 보이면 액션으로 추정한 레인지) |
| 팟이 이긴 사람에게 넘어가는 화면 | 칩이 플레이어에게 돌아온 화면을 핸드의 끝으로 보고 읽지 않음 |
| 남은 플레이어가 모두 올인 | 베팅이 끝난 것으로 보고, 보드가 깔리는 화면의 칩은 읽지 않음 |
| 플레이어 앞 숫자가 그 핸드에서 낸 누적 금액 | 스트리트별 금액으로 바꿔 읽음. 메모에 적거나, 플랍 이후 팟이 그 숫자들의 합과 같으면 저절로 알아챔 |
| 스택 숫자가 없음 | 스택 깊이와 올인은 쓰지 않고, 앞에 놓인 칩과 팟으로 액션을 복원 |
| 다음 카드가 깔리기 전에 베팅이 팟으로 모임 | 스택에서 빠졌는데 앞에 보이지 않는 칩은, 팟이 그만큼 늘었으면 그 스트리트의 베팅으로 봄. 새 스트리트 화면에서는 지난 스트리트를 마감한 금액을 넘는 부분을 새 스트리트의 베팅으로 봄 |
| 내 카드가 오기 전 블라인드만 놓인 화면 | 관전 화면처럼 따라가다가 내 카드가 보이면 그 핸드를 내 핸드로 바꿈 (앞 프레임 유지) |
| 팟이 넘어가거나 카드가 뒤집힌 화면 | 마지막 베팅에 응하지 않고 스택도 그대로인 사람은 폴드, 나머지는 콜로 마감 |
| 팟 숫자가 베팅 표시보다 먼저 바뀜 (칩이 움직이는 중) | 내 차례가 아닐 때 팟이 칩 합보다 앞선 프레임은 잠시 두고, 다음 프레임이 맞으면 지나가는 순간으로 버림. 다음 프레임도 안 맞거나 새 핸드면 그대로 씀. 버린 프레임 대부분이 결국 쓰이는 소스는 더 미루지 않음 |
| 내 카드가 프레임마다 다르게 읽힘 (한 장이 다른 카드에 가려짐) | 두 번째로 많은 읽기가 2프레임 이상이고 첫째의 절반 이상이면, 그 화면에서 내 카드만 따로 다시 읽어(구석 숫자로 읽으라고 지시) 3프레임만큼으로 셈. 한 핸드에 2번까지 |
| 내 자리 표시가 화면마다 다름 (딜러 인물이나 쇼다운에서 카드를 연 상대를 내 자리로 읽음) | 소스마다 내 카드가 보인 자리를 기억해, 다른 자리를 가리킨 화면은 그 자리로 바로잡고 그 수를 셈. 좌석은 화면 위치로 맞춤 |

엔진이 친 핸드를 이 화면들로 바꿔 넣었습니다. 100bb 동일 스택과 4~250bb 혼합 스택 각각 250핸드, 화면 8종류(쇼다운에서 칩을 앞에 남겨 두는 화면 포함)를 시험했고, 16가지 모두에서 액션 기록이 엔진과 같고 다시 읽은 핸드가 0이었으며 기록된 카드도 모두 맞았습니다. 이전에는 모든 카드가 보이는 화면에서 99핸드 모두 첫 화면에서 멈췄고, 폴드 뒤에도 내 카드가 남는 화면에서는 195핸드 중 193핸드를 중간부터 다시 읽었습니다.

인식 단계에는 "내 자리는 프로그램을 쓰는 자리(보통 아래 가운데, 또는 메모가 가리키는 자리) 하나만, 폴드한 뒤에도 표시하고, 관전 화면이면 표시하지 않는다", "폴드한 카드가 화면에 남아 있어도 핸드에서 빠진 것으로 읽는다", "테이블에 그려진, 카드만 나눠 주는 딜러는 자리가 아니다", "숫자로 보이지 않는 스택은 비워 둔다", "앞에 놓인 숫자가 핸드 누적이면 그대로 적고 그렇다고 표시한다"고 지시합니다. 내 자리가 여러 곳으로 읽히면 소스 메모에 내 자리를 적어 달라고 표시합니다. 아래 외부 게임 확인에서 실제 화면으로 시험했습니다.

**기록으로 배우는 모델.** 실전 온라인 모델은 2009년 실전 플레이어의 습관이라, 연구용 소프트웨어나 직접 만든 게임의 플레이어와는 다를 수 있습니다. 매일 학습(`daily`)은 클라우드에서 봇끼리의 핸드로 돌기 때문에 이 차이를 메우지 못합니다. 그래서 창에서 따라간 핸드 자체로 배웁니다.

- 실전 온라인 모델의 통계를 500핸드 분량으로 줄여 바탕에 깔고, 그 위에 프로그램(소스 이름)별로 그 프로그램 플레이어들의 액션을 더합니다. 기록이 적으면 실전 온라인 모델에 가깝고, 쌓일수록 그 프로그램의 플레이가 앞섭니다.
- 프로그램마다 따로 학습하고, 통합 프로필은 실전 온라인 모델 그대로 둡니다. 처음에는 통합 프로필에 모든 프로그램의 기록을 합쳤는데, 그러면 기록이 없는 새 프로그램이 다른 프로그램의 습관으로 읽혔습니다. 거친 테이블 4,000핸드만 학습한 뒤 짠 테이블을 읽게 했더니 실전 온라인보다 오차가 0.95 ± 0.30%p 컸습니다. 지금은 차이가 0이고, 두 프로그램을 함께 학습해도 각 프로그램은 따로 학습했을 때와 같은 만큼 나아집니다(짠 테이블 −0.37 ± 0.25%p, 둘 다).
- 숨은 카드는 기존 학습과 같은 방식(EM)으로 추정하고, 쇼다운에서 공개된 카드는 그대로 씁니다. 인식 단계가 쇼다운에 뒤집힌 다른 플레이어의 카드도 읽고, 추적기는 그 화면의 칩은 읽지 않고 카드만 기록에 남깁니다(팟이 이긴 사람에게 넘어가는 중일 수 있어서). 카드가 뒤집혔다는 것은 베팅이 끝났다는 뜻이므로, 마지막 라운드의 남은 체크도 채웁니다.
- 모든 카드가 보이는 프로그램은 모든 핸드의 카드를 알려 주므로 가장 많이 가르칩니다. 짠 테이블 1,000핸드로 학습했을 때 실전 온라인 대비 오차가 일반 화면 기록으로는 0.40 ± 0.17%p, 모든 카드가 보이는 관전 화면 기록으로는 0.67 ± 0.24%p 줄었습니다. 관전 화면에는 내 자리가 없으므로 모든 플레이어의 액션을 배웁니다.
- 처음부터 따라간 핸드만 씁니다. 중간에 화면이 이어지지 않아 다시 읽은 핸드(잘못 읽었을 가능성), 플랍부터 본 핸드, 팟을 읽지 못한 핸드, 이름 없는 소스의 핸드는 뺍니다. 내 액션도 뺍니다. 모델은 상대를 읽는 데 쓰기 때문입니다.
- 직접 학습하려면 `python -m pokerlab learn hands.jsonl`을 씁니다. 결과는 `data/action_model_live.json`에 저장되고, 이 파일은 각자의 컴퓨터에서 만들어집니다.

엔진이 친 핸드를 창 화면처럼 프레임으로 바꿔 추적기에 넣고, 그 기록으로 학습한 모델을 같은 프로그램의 새 핸드 1,500개에서 실전 온라인 모델과 비교했습니다. 상대가 실제로 든 핸드 기준 승률과의 평균 오차이고, 같은 결정 시점에서 짝지어 잰 차이입니다. 두 프로그램 모두 2009년 실전 플레이어와 다르게 치는 봇 6명입니다.

| 프로그램 | 랜덤 핸드 가정 | 실전 온라인 | 기록 250핸드 | 1,000핸드 | 4,000핸드 |
|---|---|---|---|---|---|
| 짠 테이블 (`nit` 2, `tag`, `tag_range`, `pro`, `human`) | 12.82%p | 11.34%p | 11.21 (−0.13 ± 0.14) | 10.98 (−0.36 ± 0.17) | 10.76 (−0.58 ± 0.24) |
| 거친 테이블 (`pro` 2, `maniac`, `station`, `lag`, `tag`) | 14.37%p | 14.36%p | 14.11 (−0.25 ± 0.29) | 14.14 (−0.23 ± 0.41) | 14.09 (−0.27 ± 0.46) |

짠 테이블에서는 1,000핸드부터 분명히 나아졌고, 4,000핸드에서는 실전 온라인 모델이 랜덤 가정보다 나았던 폭(1.48%p)의 약 40%만큼 더 줄었습니다. 거친 테이블에서는 무작위에 가까운 플레이어가 섞여 어떤 모델로도 잘 읽히지 않았고, 줄기는 했지만 유의하지 않았습니다. 나빠진 경우는 없었습니다. 바탕 모델의 무게를 2,000핸드나 8,000핸드로 두면 변화가 더 작았습니다. 이 수치는 인식이 정확하다는 가정 아래의 값입니다.

**키와 인식 서비스.** 인식은 Anthropic Claude API나 Google Gemini API로 합니다. 키는 `pokerlab serve`를 띄우는 컴퓨터의 환경 변수로 줍니다(설치와 넣는 방법은 위 '설치와 실행'). Claude 키만 있으면 Claude를, Gemini 키가 있으면 Gemini를 쓰고, `POKERLAB_VISION_PROVIDER=claude`(또는 `gemini`)로 정할 수 있습니다. 프레임은 인식을 위해 그 서비스로 전송되며, 창에 보이는 다른 플레이어의 닉네임이 함께 나갑니다. claude.ai 구독과 API 키는 별개이고, API는 쓴 토큰만큼 과금됩니다.

- **Claude**: 공식 `anthropic` 패키지로 Messages API를 부르고, 답을 JSON 스키마로 고정합니다(structured outputs). 기본 모델은 Claude Opus 5.5이며 `POKERLAB_VISION_MODEL=claude-sonnet-5-5`처럼 바꿉니다. 사고 깊이는 `low`(`POKERLAB_VISION_EFFORT`)입니다. `POKERLAB_VISION_COMPACT=1`이면 짧은 키로 답하게 해 출력 토큰이 절반이 되지만, 정확도가 조금 떨어져 기본으로 두지 않았습니다(아래 '짧은 답 형식'). Opus 5.5와 Sonnet 5.5에는 서버 측 대체(fallbacks)를 켜 두어, 드물게 요청이 거절되면 같은 호출 안에서 API가 고른 다른 모델이 이어 읽습니다. 지시문은 매 프레임 같아서 캐시됩니다.
- **Gemini**: `GEMINI_API_KEY`, 기본 모델 `gemini-4-hydrogen`. 실제로 호출해 본 적은 없습니다.

**Claude로 잰 인식 정확도.** 정답을 아는 테이블 화면(엔진이 친 핸드의 한 순간을 1280×800 클라이언트 화면처럼 그린 것)을 30장 만들어 세 모델로 읽었습니다. 6인 15장, 9인 15장이고, 화면은 내 카드만 보이는 화면 12장, 모든 카드가 보이는 화면 9장, 관전 화면 9장입니다.

|---|---|---|---|
| 응답 시간 (중앙값 / 90%) | 3.1초 / 3.8초 | 4.5초 / 5.3초 | 6.0초 / 7.4초 |
| 프레임당 비용 | 약 $0.0006 | 약 $0.011 | 약 $0.022 |
| 스택 | 이름을 읽은 자리 전부 맞음 | 전부 맞음 | 전부 맞음 |
| 앞에 놓인 칩 (자리별) | 89% | 93% | 99% (이름을 다르게 읽은 자리 빼면 전부) |
| 보드 / 팟 | 29 / 30장 | 30 / 30장 | 30 / 30장 |
| 내 카드 (내 자리가 있는 21장) | 13장 | 18장 | 20장 |
| 모든 카드가 보이는 화면의 상대 카드 | 31장 중 6장 | 28장 | 29장 |
| 추적기에 넣을 값이 모두 맞은 프레임 | 약 10장 | 약 23장 | 28장 |

- Opus 5.5가 틀린 두 장은 딜러 버튼이었는데, 테스트 그림에서 버튼이 두 자리 사이에 애매하게 놓인 프레임이었습니다(세 모델 모두 틀림). 그 밖에 이름 한 글자를 다르게 읽은 경우가 있었지만(`Jjang9` → `Jiang9`), 추적은 자리 위치로 하므로 영향이 없습니다.
- 관전 화면에서는 세 모델 모두 아래쪽 자리를 내 자리로 표시했습니다. 추적기가 이를 관전 화면으로 다시 읽습니다(내 카드가 보이지 않는 표시는 무시하고, 관전 중인 핸드에서 쇼다운 때 아래쪽 카드가 보이면 그 자리의 카드로 봄).
- Haiku 5.5는 싸고 빠르지만 칩과 공개된 카드를 자주 틀려 추적에는 맞지 않습니다. Sonnet 5.5는 Opus 5.5의 절반 비용에 1.5초 빠르고, 앞에 놓인 칩을 조금 더 틀립니다.
- 측정에 쓴 비용은 약 1.4달러입니다. 이 그림들은 실제 프로그램 화면보다 단순하므로 실제 정확도는 이보다 낮을 수 있습니다. 실제 프로그램에서는 위의 '인식 품질' 지표로 확인할 수 있습니다.
- **실제 경로 확인**: 브라우저의 창 소스 → 서버 → Claude Opus 5.5 → 추적기 → 기록까지 한 핸드(화면 11장 + 다음 핸드 첫 화면)를 실제로 돌렸습니다. 읽은 화면은 한 장에 5~8초 걸렸고, 칩 합계는 모두 맞았으며, 기록된 액션은 엔진과 같았습니다. 다만 쇼다운 화면을 감지하지 못해 마지막 콜 하나가 빠졌는데, 위의 변화 감지를 고친 원인입니다.

**외부 게임으로 확인.** 다른 사람이 만든 브라우저 포커 게임 두 개를 이 컨테이너에서 띄워 직접 플레이하며 화면을 저장하고, Claude Opus 5.5로 읽혀 추적기에 넣었습니다. 쓴 비용은 약 1.7달러입니다.

| | HTML5 게임 (오픈소스 브라우저 게임, 6인) | Flash 게임 (Governor of Poker 데모를 Ruffle로 실행, 5인) |
|---|---|---|
| 화면 | 이름판에 스택, 앞에 베팅. 올인은 "ALL IN (490)"처럼 핸드 누적으로 표시 | 스택 숫자 없음, 앞의 숫자가 핸드 누적 금액, 내 자리는 위 가운데, 아래 가운데에 딜러 인형 |
| 읽은 프레임 | 바뀐 화면 24장 (한 장 5~8초) | 1.5초마다 45장, 두 핸드 (한 장 4~8초) |
| 읽기 | 스택·팟 정확, 칩 합계 12/12 일치. 내 카드 한 장(J♣)이 다른 카드에 가려 5장에서 K♣로 읽힘 | 소스 메모(내 자리, 딜러, 누적 금액)를 주면 보드·내 카드·금액·팟이 거의 모두 맞음. 메모 없이 읽힌 8장 중 4장은 딜러를 내 자리로 읽음 |

고친 것은 위 '아무 때나 들어오는 프레임'과 '프로그램마다 다른 화면'에 반영했습니다. 그 뒤 소스 메모 없이 Flash 게임을 읽은 8장(4장에서 딜러를 내 자리로 읽음)도 다시 넣어 봤습니다. 전에는 그 4장에서 좌석 전체가 한 칸씩 돌아가 엉뚱한 기록이 남았고 품질 지표에도 드러나지 않았는데, 지금은 4장 모두 내 자리를 바로잡고 "내 자리를 다른 곳으로 읽은 화면 4/8"로 표시합니다.

**아직 확인하지 못한 것.** 위 수치는 "읽은 값이 맞다면"의 결과입니다. 실제로 돌려 본 것은 인식 이후의 단계입니다. 브라우저 시험은 창 선택을 대신하는 가짜 영상과, 인식을 대신하는 저장된 값 재생(`POKERLAB_VISION_REPLAY=값.json`)으로 했습니다. 실제 창 선택 대화상자와 Gemini 인식은 한 번도 돌려 보지 못했습니다. Claude 인식은 위의 테스트 그림과 외부 브라우저 게임 두 개로 쟀고, 연구용·기록용 프로그램의 실제 화면으로는 아직 재지 못했습니다. 인식 한 번에 몇 초가 걸리고 호출마다 비용이 들며, 프로그램 화면에 따라 읽기 정확도가 다를 것입니다.

**직접 계산.** 두 번째 탭은 창 없이 쓰는 계산기입니다. 카드를 클릭해 내 핸드와 보드를 채우면 승률, 승/무/패 비율, 최종 족보 확률, 다음 카드별 승률, 상대 수별 승률이 계산됩니다. 상대를 추가해 액션(예: 오픈 레이즈 → 플랍 벳)을 넣으면 추정 레인지가 13×13 표로 표시되고 승률이 그 레인지 기준으로 바뀝니다.

|---|---|
| `--players N` | 지금 판에 남은 인원, 나 포함 (2~10) |

액션 단어는 프리플랍 `limp open call 3bet call3bet 4bet check`, 플랍 이후 `check bet call raise callraise reraise`입니다. 단어 뒤의 숫자는 팟 대비 크기(%)입니다. `bet66`은 팟의 66% 벳, `raise100`은 콜한 뒤의 팟만큼 올린 레이즈, `call50`은 팟의 절반 크기 벳에 콜한 것입니다. 프리플랍 오픈은 `open3x`, `call3x`(3bb 오픈에 콜)처럼 빅 블라인드 배수로도 씁니다. 숫자 대신 `allin`을 붙이면 올인입니다(`betallin`, `raiseallin`, `callallin`은 올인에 콜, `shove`는 줄임말). 크기를 생략하면 모든 크기의 평균으로 해석합니다.

스택은 핸드를 시작할 때 상대의 칩과 그 상대에 맞선 가장 큰 스택 중 작은 쪽입니다. 스택을 주면 각 액션 시점에 남은 칩이 팟의 몇 배인지를 줄을 따라 계산합니다. 이때 크기를 적지 않은 벳은 흔한 크기(팟의 66%, 오픈 3bb)로, 모든 벳은 한 명이 콜한 것으로 가정합니다. 스택을 생략하면 모든 깊이의 평균으로 해석합니다. 좌석은 `ep`(얼리), `mp`(미들), `co`(컷오프), `btn`(버튼), `sb`, `bb`이고 `utg`, `hj`도 받습니다. 액션 한 줄에는 그때 누가 폴드해 있었는지가 없으므로, 프리플랍은 그 좌석 앞이 모두 폴드한 상황으로 가정합니다.

모든 플레이어의 승률을 한 번에 보려면 `matchup`을 씁니다. 핸드가 전부 정해져 있으면 남은 보드를 전수 계산합니다.

### Python

```python
from pokerlab.equity import equity, matchup, next_card
from pokerlab.inference import range_from_line
from pokerlab.preflop import parse_range

equity("AsKs", "Qs Js 2d", n_opponents=3)                        # .equity .win .tie .ci95 .hand_dist
equity("AsKs", n_opponents=5, precision=0.001)                   # ±0.1%p가 될 때까지
equity("AhKd", ranges=[parse_range("QQ+")])                      # 상대 레인지 지정
equity("AsKs", "Qs Js 2d", ranges=[range_from_line("open/bet", "AsKs", "Qs Js 2d")])
matchup(["AsKs", parse_range("TT+"), None], "Qs Js 2d")          # 핸드, 레인지, 랜덤 핸드
next_card("AsKs", "Qs Js 2d")                                    # {카드: 그 카드가 나온 뒤 승률}
```

## 레인지 추정 모델의 효과

모델은 "어떤 상황에서 어떤 강도의 핸드로 어떤 액션을 했는가"를 센 표입니다. 상대의 액션을 관찰할 때마다 베이즈 규칙으로 1,326개 콤보의 가중치를 갱신합니다.

- **액션**: 폴드, 체크·콜, 벳·레이즈를 크기에 따라 셋으로 나눈 것(작게, 보통, 크게), 그리고 올인. 크기는 콜 금액을 넘겨 넣은 칩을 콜한 뒤의 팟으로 나눈 값이고, 45% 미만이 작게, 90% 이상이 크게입니다. 상대가 받을 수 있는 칩을 전부 넣은 벳은 크기와 상관없이 올인입니다(내 스택이 더 커서 상대만 올인이 되는 벳도 포함).
- **상황**: 스트리트, 그 스트리트에서 이미 나온 레이즈 수, 콜 가격, 스택 깊이, 남은 인원, 테이블 크기(1:1 / 3~6인 / 7인 이상), 포지션.
- **콜 가격**: 콜할 금액을 팟으로 나눈 값으로, 없음 / 싸다 / 보통 / 비싸다 네 단계입니다. 경계는 팟의 45%와 90% 크기 벳이 만드는 가격(0.31, 0.47)입니다.
- **스택 깊이**: 콜한 뒤에도 더 걸 수 있는 칩(내 칩과 상대 중 가장 큰 스택 가운데 작은 쪽)을 콜한 뒤의 팟으로 나눈 값으로, 다섯 단계입니다. 남은 칩 없음(올인을 받았거나 콜하면 올인) / 팟 1배 미만 / 1~4배 / 4~20배 / 20배 이상. 100bb로 시작하면 프리플랍 첫 액션이 20배 이상, 플랍이 4~20배, 벳이 이어진 리버가 1~4배쯤입니다.
- **포지션**: 프리플랍은 좌석(얼리, 미들, 컷오프, 버튼, 스몰 블라인드, 빅 블라인드), 플랍 이후는 남은 플레이어 중 행동 순서(처음, 중간, 마지막).
- **핸드 강도**: 그 보드에서 가능한 모든 핸드 중 상위 몇 %인지를 10구간으로 나눈 값.
- **드문 상황**: 상황은 굵은 것에서 세밀한 것으로 포개져 있고, 각 단계는 자기 데이터에 윗단계 확률 20회분을 더해 추정합니다. 몇 번 못 본 좌석은 그 테이블의 평균에 기대게 됩니다.
- **벳 종류의 추정**: 벳이 세 크기와 올인 중 무엇인지는 폴드·콜·벳 확률과 따로 추정합니다. 모든 강도의 핸드가 함께 쓰는 분포에서 출발하고, 상황을 좁힐 때는 먼저 모든 강도를 똑같이 옮긴 뒤(남은 칩이 적으면 어떤 핸드든 벳의 대부분이 올인입니다) 강도별 데이터를 반영합니다. 그래서 데이터가 보여 주는 만큼만 크기가 핸드에 대한 정보가 됩니다.

아래는 봇 자가대전으로 학습한 `selfplay` 모델입니다(`tag`/`lag`/`nit` 2~9인 대전 15,000핸드). 학습에 쓰지 않은 대전(다른 시드)에서 결정 시점 4,000개를 뽑아, 상대가 실제로 들고 있던 핸드 기준의 승률과 비교했습니다.

## 공개 핸드 히스토리로 학습한 모델

사람의 플레이를 읽으려면 사람의 데이터로 배워야 합니다. [PHH 데이터셋](https://github.com/uoftcprg/phh-dataset)(MIT 라이선스)의 두 묶음으로 학습한 모델을 함께 넣었습니다. 분석 도구(`equity`, 웹 화면)는 `online`을 기본으로 쓰고, 봇과 매일 학습은 `selfplay`를 씁니다.

| 모델 | 데이터 | 홀카드 |
|---|---|---|
| `online` | 2009년 7월 6개 사이트의 실전 캐시게임 200,609핸드 (HandHQ, 25NL~1000NL, 2~10인). 스택이 기록된 것은 161,935핸드 | 쇼다운에서 보여준 것만: 플레이어-핸드의 5.2% |
| `pro` | Pluribus와 프로 5명의 6인 게임 10,000핸드 (Brown & Sandholm 2019) | 전부 공개 |
| `selfplay` | 이 패키지의 봇 자가대전, 매일 학습으로 갱신 | 전부 공개 |

`online`에는 스테이크 구간 프로필(`nl25-50`, `nl100-200`, `nl400-600`, `nl1000`)이, `pro`에는 `pluribus`와 `pro` 프로필이 들어 있습니다. HandHQ 파일의 203,204핸드 가운데 블라인드가 음수로 적힌 2,595핸드는 팟 크기를 알 수 없어 뺐습니다. 스택이 기록되지 않은 38,674핸드(일부 사이트)는 폴드·콜·벳 학습에는 쓰고, 스택 깊이와 올인 학습에서는 뺍니다. Pluribus 데이터는 모든 핸드가 100bb로 시작합니다.

### 숨은 카드를 다루는 방법

실전 기록에서는 폴드한 핸드를 볼 수 없습니다. 보여준 핸드만 세면 끝까지 간 핸드만 남아 모델이 틀어집니다. 그래서 EM을 씁니다. 현재 모델로 각 플레이어의 숨은 핸드가 무엇이었을지를 그 판의 모든 액션을 근거로 추정하고, 그 확률만큼 나눠 세고, 다시 추정하기를 반복합니다. 카드가 공개된 플레이어는 그대로 한 번씩 셉니다.

학습은 2단계입니다. 먼저 테이블 크기와 포지션을 뺀 굵은 상황으로 수렴시키고, 그 답에서 출발해 세밀한 상황을 학습합니다. 두 단계 모두 숨은 핸드를 추정할 때는 폴드·콜·벳만 보고, 벳 크기와 콜 가격, 스택 깊이와 올인은 그 추정에 따라 세기만 합니다(이유는 아래 '벳 크기와 콜 가격의 효과'). 세밀한 상황을 백지에서 바로 학습하면 실전 데이터에서 강한 핸드와 약한 핸드의 구분이 흐린 모델이 나왔습니다. 가장 약한 10% 핸드의 오픈 레이즈 빈도가 6%였고, 2단계 학습에서는 1%입니다.

정답을 아는 자가대전 데이터로 절차를 확인했습니다. 6만 핸드에서 실전 기록과 같은 비율(플레이어-핸드의 5.2%)만 카드를 남기고 학습한 뒤, 새 핸드 2,500개로 평가했습니다.

| 학습 방법 | 전체 정보 모델과의 확률 차이 | 액션당 로그우도 | 승률 평균 오차 |
|---|---|---|---|
| 전체 정보로 학습 (기준) | 0 | −0.399 | 11.79%p |
| EM 2단계 (카드 5.2%만 공개) | 3.5% | −0.417 | 11.78%p |
| EM 2단계, 벳 크기와 콜 가격도 추정에 사용 | 3.4% | −0.416 | 11.74%p |

로그우도는 벳 크기까지 맞히는 기준입니다. 봇은 핸드 강도에 따라 기계적으로 행동해서, 벳 크기를 넣기 전의 측정에서는 백지에서 한 번에 학습해도 결과가 같았습니다(확률 차이 3.0%). 2단계가 차이를 만든 것은 실전 데이터입니다.

### 실전 데이터에서의 결과

학습에 쓰지 않은 파일의 실전 4만 핸드에서, 각 모델이 실제 액션을 얼마나 잘 설명하는지입니다. 로그우도는 폴드·콜·벳 세 가지를 맞히는 기준이고(벳 크기와 올인까지 맞히는 기준으로는 `online`이 −0.868), "공개 핸드 적중"은 쇼다운에서 공개된 9,731핸드에 대해, 그 플레이어의 액션으로 추정한 레인지가 실제 핸드에 준 확률이 균등 추측의 몇 배인지(기하평균)입니다.

| 모델 | 액션당 로그우도 | 공개 핸드 적중 |
|---|---|---|
| `selfplay` | −1.600 | 0.00배 |
| `pro` | −0.832 | 1.32배 |
| 공개된 핸드만 세기 (벳 크기를 넣었을 때 측정) | −6.362 | 1.34배 |
| `online` (EM 2단계) | −0.692 | 2.25배 |

`selfplay`의 0.00배는 봇이 절대 하지 않는 액션(약한 핸드의 레이즈 등)을 사람이 하기 때문입니다. 그런 핸드에 거의 0의 확률을 주면 기하평균이 0으로 떨어집니다.

승률 추정의 정확도는 모든 홀카드를 아는 Pluribus 데이터로 쟀습니다. 1만 핸드에서 결정 시점을 하나씩 뽑았고, `pro`는 5겹 교차검증(학습에 쓰지 않은 핸드로 평가)입니다.

| 상대 레인지 | 평균 절대 오차 | RMSE | 플랍 이후 편향 |
|---|---|---|---|
| 랜덤 핸드 가정 | 11.65%p | 18.47%p | +11.0%p |
| `selfplay` | 10.77%p | 18.89%p | +11.0%p |
| `online` | 10.20%p | 16.16%p | +3.4%p |
| `pro` (교차검증) | 10.13%p | 16.00%p | +1.3%p |

2009년 온라인 플레이어로 학습한 `online`이 프로 본인들의 데이터로 학습한 `pro`에 가깝습니다(같은 결정 시점에서 평균 오차 차이 0.08 ± 0.06%p). `selfplay`는 `online`보다 평균 오차가 0.57 ± 0.17%p 크고, 큰 오차가 많아 RMSE 차이는 더 큽니다. 70~80%라고 계산했을 때 실제 승률은 `selfplay` 54%, `online` 69%였습니다.

학습된 습관의 예입니다. 가장 약한 10% 핸드에서 가장 강한 10% 핸드 순서로, 둘만 남은 플랍에서 체크가 돌아왔을 때 벳하는 빈도입니다.

| 모델 | 최약 | | | | | | | | | 최강 |
|---|---|---|---|---|---|---|---|---|---|---|
| `online` | 19% | 18% | 22% | 26% | 33% | 42% | 42% | 47% | 55% | 63% |
| `pro` | 17% | 22% | 25% | 25% | 26% | 32% | 32% | 29% | 32% | 52% |
| `selfplay` | 10% | 9% | 9% | 9% | 11% | 22% | 54% | 85% | 99% | 100% |

봇은 강할 때만 벳하고, 사람은 약한 핸드로도 벳하며 강한 핸드로도 체크합니다. 봇으로 배운 모델이 사람의 액션을 잘못 읽는 이유입니다.

### 포지션과 테이블 크기의 효과

같은 액션이라도 좌석에 따라 뜻이 다릅니다. 앞이 모두 폴드했을 때 레이즈로 들어오는 빈도입니다.

| | 6인 미들 | 6인 컷오프 | 6인 버튼 | 6인 스몰 블라인드 | 9인 얼리 | 1:1 버튼 |
|---|---|---|---|---|---|---|
| `online` | 17% | 24% | 35% | 30% | 9% | 58% |
| `pro` | 20% | 29% | 43% | 32% | - | - |

분석 도구에서도 같은 "오픈 레이즈 후 플랍 벳"의 추정 레인지 폭이 좌석에 따라 달라집니다. 6인 테이블에서 좌석을 모르면 23%, 컷오프 30%, 버튼 45%, 9인 테이블 UTG는 14%, 1:1 테이블 버튼은 66%입니다.

이 두 가지를 넣기 전후를 같은 데이터로 비교했습니다. 벳 크기를 넣기 전에 잰 값이며, 보류 핸드를 다시 뽑기 전이라 위 표의 숫자와는 조금 다릅니다.

| 측정 | 넣기 전 | 넣은 후 |
|---|---|---|
| `online`: 실전 보류 4만 핸드 액션당 로그우도 | −0.721 | −0.702 |
| `online`: 실전 보류 공개 핸드 적중 | 2.12배 | 2.17배 |
| `pro`: Pluribus 교차검증 액션당 로그우도 | −0.459 | −0.444 |
| `human` 봇의 1:1 VPIP / PFR (실제 53.0% / 35.5%) | 38.8% / 25.0% | 52.8% / 35.1% |
| `human` 봇의 9인 VPIP / PFR (실제 21.4% / 9.3%) | 23.2% / 11.8% | 20.9% / 9.0% |
| `online`: Pluribus 승률 평균 오차 | 10.17%p | 10.23%p |
| `pro`: Pluribus 승률 평균 오차 (교차검증) | 10.17%p | 10.17%p |
| `selfplay`: 보류 자가대전 승률 평균 오차 | 11.3%p | 11.4%p |
| `pro` 모델을 실전 온라인 데이터에 적용한 공개 핸드 적중 | 1.88배 | 1.49배 |

액션을 설명하는 능력은 좋아졌고, 개선의 대부분은 포지션에서 나왔습니다(테이블 크기만 넣으면 로그우도 −0.718). 테이블 크기별 습관도 재현됩니다. 반면 승률 추정 오차는 Pluribus 데이터에서 달라지지 않았습니다. 그리고 모델이 세밀해진 만큼 집단 고유의 습관을 더 담게 되어, 한 집단의 모델을 다른 집단에 적용했을 때는 오히려 나빠진 경우가 있습니다(마지막 행).

### 벳 크기와 콜 가격의 효과

모델에 담긴 습관의 예입니다(`online`). 둘만 남은 리버에서 체크가 돌아왔을 때 벳한 핸드 가운데 작은 벳과 큰 벳의 비율이며, 가장 약한 10% 핸드에서 가장 강한 10% 핸드 순서입니다.

| 리버 벳의 크기 | 최약 | | | | | | | | | 최강 |

| 크게 (90% 이상) | 26% | 25% | 21% | 21% | 19% | 18% | 16% | 14% | 15% | 20% |

| 보통 | 95% | 96% | 93% | 93% | 80% | 69% | 55% | 39% | 16% | 2% |
| 비싸다 (90% 이상) | 99% | 99% | 97% | 96% | 87% | 77% | 71% | 52% | 24% | 2% |

분석 도구에서는 같은 액션이라도 크기에 따라 결과가 달라집니다. 내가 버튼에서 A♠K♣로 매 스트리트 벳했고 빅 블라인드가 모두 콜한 경우입니다(보드 K♠9♦4♣7♥2♠).

| 빅 블라인드의 액션 | 추정 레인지 폭 | 내 승률 |
|---|---|---|
| `bb: call/call/call/call` (크기 모름) | 18% | 82.1% |
| `bb: call3x/call33/call33/call33` (매번 팟의 1/3 벳에 콜) | 22% | 86.9% |
| `bb: call3x/call100/call100/call100` (매번 팟 크기 벳에 콜) | 15% | 72.5% |

크기를 넣으면서 학습 절차를 하나 바꿨습니다. 처음에는 숨은 카드를 추정할 때 벳 크기와 콜 가격까지 근거로 썼는데, 그렇게 학습한 모델은 보류 핸드의 공개 핸드 적중이 크기를 쓰지 않을 때보다 낮았습니다(2.08배 대 2.20배). 큰 벳은 상대가 폴드해서 카드가 공개되지 않고 끝나는 일이 많고, 그런 핸드를 EM이 자기 추정으로 채우면서 "큰 벳은 약한 핸드"라는 쪽으로 쏠렸습니다. 플랍에서 약한 쪽 30% 핸드가 벳했을 때 큰 벳의 비율이 그 모델에서는 46%였는데, 보류 핸드에서 실제로 공개된 그런 벳 122건에서는 23%였습니다. 지금은 숨은 카드를 추정할 때 크기와 가격을 보지 않고, 추정된 핸드에 따라 크기별로 세기만 합니다. 이렇게 학습한 모델에서는 같은 비율이 21%입니다. 공개된 핸드는 쇼다운까지 간 핸드라 전체를 대표하지는 않지만, 보류 핸드의 적중도 이 절차가 가장 높았습니다.

정답을 아는 자가대전 데이터에서는 결과가 반대였습니다. 봇은 약한 핸드로 큰 벳을 하지 않는데(플랍에서 약한 쪽 40% 핸드의 벳 중 큰 벳 0%), 크기까지 추정에 쓴 학습은 이를 그대로 복원했고(0~1%) 지금 절차는 흐리게 복원했습니다(9~12%). 전체 지표는 위 표처럼 비슷합니다. 봇은 핸드 강도만으로 행동하지만 사람은 플레이어마다 크기 습관이 다르고, 그 습관까지 숨은 핸드 탓으로 돌리면 틀리는 것으로 보입니다. 지금 절차는 크기의 정보를 덜 쓰는 쪽으로 틀리는 보수적인 선택이며, `fit-history --use-sizes`로 바꿀 수 있습니다.

넣기 전후를 같은 핸드로 비교했습니다. "넣기 전"은 이전 모델을 같은 보류 핸드에 적용한 값이고, "넣은 후"는 스택 깊이와 올인을 넣기 전에 잰 값입니다.

|---|---|---|
| `online`: 실전 보류 4만 핸드 폴드·콜·벳 로그우도 | −0.6996 | −0.6959 |
| `online`: 실전 보류 공개 핸드 적중 | 2.199배 | 2.226배 |
| `online`: Pluribus 4,000핸드 공개 핸드 적중 | 1.304배 | 1.307배 |
| `online`: Pluribus 승률 평균 오차 | 10.23%p | 10.22%p |
| `pro`: Pluribus 교차검증 공개 핸드 적중 | 1.345배 | 1.342배 |
| `pro`: Pluribus 승률 평균 오차 (교차검증) | 10.17%p | 10.16%p |

- 승률 추정 오차는 의미 있게 줄지 않았습니다. Pluribus 데이터의 같은 결정 시점에서 넣기 전과의 차이는 `online` −0.01 ± 0.01%p, `pro` −0.02 ± 0.02%p입니다.
- 한 집단의 모델을 다른 집단에 적용하면 오히려 나빠집니다(마지막 두 행). 벳 크기 습관은 집단마다 달라서, 프로의 크기 습관으로 2009년 온라인 플레이어를 읽거나 봇의 습관으로 프로를 읽으면 틀립니다. 포지션을 넣었을 때와 같은 현상입니다.
- 자가대전 데이터에서는 차이가 거의 없습니다. 봇은 큰 벳을 강한 핸드로만 하지만 그런 벳은 전체 벳의 20% 정도이고, 받는 벳의 크기도 팟의 절반에서 1배 사이로 좁아 콜 가격이 거의 갈리지 않습니다.

### 스택 깊이와 올인의 효과

실전 데이터에서 올인은 리버로 갈수록 많습니다. 벳과 레이즈 가운데 올인의 비율은 프리플랍 4%, 플랍 5%, 턴 8%, 리버 12%이고, 받은 벳이 올인(콜하면 남는 칩이 없음)인 비율은 1%, 4%, 6%, 11%입니다. 올인 여부는 남은 칩이 거의 결정합니다. 리버 벳 가운데 올인의 비율은 남은 칩이 팟 1배 미만이면 68%, 1~4배면 7%, 4배 이상이면 1% 미만입니다.

모델에 담긴 습관의 예입니다(`online`). 둘만 남은 리버에서 벳을 받았을 때 폴드하는 빈도이며, 가장 약한 10% 핸드에서 가장 강한 10% 핸드 순서입니다.

| 콜한 뒤 남는 칩 | 최약 | | | | | | | | | 최강 |
|---|---|---|---|---|---|---|---|---|---|---|
| 없음 (올인을 받음) | 100% | 97% | 95% | 96% | 84% | 72% | 68% | 46% | 22% | 2% |
| 팟의 1~4배 | 96% | 96% | 92% | 92% | 79% | 65% | 50% | 34% | 13% | 1% |
| 팟의 4~20배 | 97% | 96% | 92% | 91% | 73% | 60% | 46% | 29% | 12% | 1% |

올인은 중간 강도 핸드가 더 많이 폴드합니다. 그래서 올인에 콜한 상대는 더 강한 쪽으로 읽힙니다. 반대로 남은 칩이 적을 때 체크가 돌아오면 약한 핸드의 벳이 늘어납니다. 가장 약한 10% 핸드가 리버에서 벳하는 빈도는 남은 칩이 팟 1배 미만일 때 57%, 20배 이상일 때 25%입니다.

분석 도구에서의 예입니다. 내가 버튼에서 A♠K♣로 매 스트리트 벳했고 빅 블라인드가 모두 콜한 경우입니다(보드 K♠9♦4♣7♥2♠).

| 빅 블라인드의 액션 | 스택 | 추정 레인지 폭 | 내 승률 |
|---|---|---|---|
| `bb: call/call/call/call` | 모름 | 18% | 82.1% |
| `bb: call/call/call/callallin` (리버 올인에 콜) | 모름 | 18% | 72.3% |
| `bb: call/call/call/callallin` | 30bb | 19% | 76.4% |
| `bb: call/call/call/callallin` | 100bb | 16% | 66.2% |

같은 "올인에 콜"이라도 30bb에서는 작은 벳에 콜한 것이고 100bb에서는 팟보다 큰 벳에 콜한 것이라 읽는 결과가 다릅니다.

- 개선은 스택 깊이에서 나왔습니다. 스택 깊이를 가리면 2.225배로 돌아가고, 올인을 "크기 모르는 벳"으로 바꿔도 2.250배 그대로입니다. 남은 칩을 알면 그 벳이 올인인지는 대부분 정해지기 때문입니다.
- 승률 추정 오차는 Pluribus 데이터에서 아주 조금 줄었습니다. `online` −0.02 ± 0.02%p, 리버만 보면 −0.43 ± 0.27%p입니다. 이 데이터는 모든 핸드가 100bb로 시작하고 올인이 벳의 1~2%(리버 11%)뿐이라 차이가 날 자리가 적습니다.

- 스택 깊이와 올인을 숨은 카드 추정에까지 쓰는 학습은 따로 비교하지 않았습니다. 벳 크기에서 확인한 것과 같은 이유로 쓰지 않는 쪽을 택했습니다.

### 사람처럼 치는 봇

`human`과 `pro` 봇은 각 상황에서 자기 핸드 강도 구간의 폴드, 콜, 크기별 벳, 올인 빈도를 모델에서 찾아 그 비율대로 행동합니다. 상황에는 그때 남은 스택도 들어갑니다. 벳 크기는 고른 구간 안에서 무작위로 정합니다(작게 팟의 25~44%, 보통 50~80%, 크게 90~130%). 모델이 데이터를 제대로 담았다면 이 봇의 통계가 원본 데이터와 같아야 합니다.

- `online` 모델은 2009년 온라인 캐시게임, `pro` 모델은 한 번의 실험에 참가한 프로들의 플레이입니다. 지금의 게임이나 특정 상대의 습관과는 다를 수 있습니다.
- 챔피언과 `selfplay` 모델은 이 봇 풀의 플레이에서 배운 것이라 사람 상대 수익률로 읽으면 안 됩니다.
- 레인지 모델의 상황 구분은 거칩니다(벳 크기와 콜 가격 각 3단계, 스택 깊이 5단계, 레이즈 수 0/1/2+, 남은 인원 2/3/4/5+, 테이블 크기 3단계).
- 스택 깊이는 실전 데이터에서 숏스택과 올인 상황을 읽는 데만 도움이 됐습니다. 100bb로만 치는 자가대전과 Pluribus 데이터에서는 차이가 없거나 아주 작았습니다. 기본 자가대전은 매 핸드 100bb로 시작하므로, 대회 형식 핸드(`daily --formats`)를 넣기 전의 `selfplay` 모델은 프리플랍 숏스택 상황을 본 적이 없습니다.
- 액션을 직접 입력할 때 스택 깊이는 가정 위에서 계산됩니다(크기를 적지 않은 벳은 팟의 66%, 모든 벳은 한 명이 콜). 실제 팟과 많이 다르면 스택을 생략하는 편이 낫습니다.
- 벳 크기와 스택 깊이가 승률 추정 오차를 크게 줄이지는 못했습니다. 실전 데이터에서 상대 핸드를 맞히는 정도가 조금씩 올랐고, Pluribus 데이터의 승률 오차는 10.23%p에서 10.20%p가 됐습니다. 봇의 모델을 사람에게 적용하면 오히려 나빠집니다.
- 창 인식의 정확도는 Claude로 테스트 그림과 외부 브라우저 게임 두 개(HTML5, Flash)에서 쟀고, 연구용·기록용 프로그램의 실제 화면으로는 아직 재지 못했습니다. 사용자 컴퓨터의 실제 창 선택 대화상자도 돌려 보지 못했습니다(`python -m pokerlab check`로 키와 인식은 확인할 수 있습니다). 읽은 값이 틀리면 그 뒤의 계산도 틀리므로, 표에 보이는 값을 확인하고 쓰는 것이 좋습니다. 앤티, 스트래들, 보드를 두 번 까는 테이블은 다루지 않습니다.
- 액션을 직접 입력할 때는 그때 누가 폴드해 있었는지를 모르므로 가정이 들어갑니다(프리플랍은 앞이 모두 폴드, 플랍 이후는 지금 남은 인원 그대로). 림프가 여럿 있던 판 같은 경우에는 맞지 않습니다.
- 봇은 단순한 규칙 기반이며 균형 전략(GTO)이 아닙니다.
- 기본 자가대전은 매 핸드 스택을 100bb로 초기화하고 좌석을 섞습니다. 레이크는 없습니다. 대회 형식(`--format`)은 블라인드 표, 앤티, 일반 속도 대회의 레벨 길이가 공개 자료에 없어 추정과 가정이 섞여 있고, 테이블 하나로 대회 전체를 근사하며, 봇은 상금 구조를 모릅니다.
- 승률은 "지금 올인해서 끝까지 갔을 때"의 값입니다. 이후 베팅 라운드와 포지션의 영향은 반영하지 않습니다.
- 전수 계산은 핸드가 모두 정해진 경우, 포스트플랍 상대 1명, 턴·리버 상대 2명(레인지 없음)까지입니다. 나머지는 몬테카를로입니다.
